## Overview

OVERDRIVE is an arena shooter in the spirit of ULTRAKILL: dashing, sliding, a grapple hook, parrying, several weapons and a style meter that rewards playing aggressively. There are two ways to play. **Arena** runs four arenas (a sunset yard, a foundry with lava channels, a tower you have to climb, and a night-time reactor) of three waves each, against seven enemy types that each demand a different answer, ending in a boss. **Fast** is a time trial down a six-section descent with a run clock and splits against your best run. Kills earn XP, scaled by how stylishly you play, and levels buy weapon upgrades, including for two bolt-action sniper rifles.

There's no engine underneath. The game is 9,177 lines of C++17 plus about 570 lines of GLSL on top of SDL2 for windowing and input, OpenGL 3.3 Core for rendering and GLM for math. It builds with a Makefile on macOS, on Windows through MSYS2, and for the browser with Emscripten, which is the build running above. I built it to learn what an engine actually does for you, and the answer turned out to be mostly **time**: deciding when things happen matters more than how they're drawn.

Game code is organised as states (menu, gameplay) that own their systems. Collision is deliberately simple: the player and every wall or platform are axis-aligned boxes, overlaps are resolved by pushing the player out along the axis of least penetration, and a spatial grid, rebuilt whenever the level's walls change, keeps each query to nearby geometry.

## Hard problems

### Physics that doesn't care about your frame rate

Movement in a game like this is tuned by feel: jump height, dash distance, how much speed a grapple builds. If physics runs once per rendered frame, all of that changes with the monitor. A 144 Hz display jumps differently from a 60 Hz one. So simulation runs on a **fixed 1/60 s step**, fed by an accumulator of real elapsed time:

<CodeRef lang="cpp" repo="https://github.com/Ollie1o1/3d_shooter" file="src/GameplayState.h" lines="869-886" code={"Uint64 now = SDL_GetPerformanceCounter();\ndouble elapsed = (double)(now - prevTicks) / (double)freq;\nprevTicks = now;\naccumulator += elapsed;\nif (accumulator > 0.25) accumulator = 0.25;\n\nconst Uint8* keys = SDL_GetKeyboardState(nullptr);\nbool parryKey = keys[SDL_SCANCODE_F] != 0;\n\nwhile (accumulator >= PHYSICS_DT) {\n    prevCamPos = player.camera.position;\n    if (hitStopFrames > 0) {\n        --hitStopFrames;  // freeze simulation, consume one tick\n    } else {\n        physicsTick(PHYSICS_DT, keys, parryKey);\n    }\n    accumulator -= PHYSICS_DT;\n}"} />

Two details do a lot of work here. The accumulator is **clamped at 0.25 s**, so a stall (a window drag, a breakpoint) can't make the game try to catch up on hundreds of ticks at once, the classic "spiral of death". And **hit-stop**, the brief freeze when a hit lands, is implemented by consuming ticks without simulating, so it's frame-rate independent for free.

Running physics at 60 Hz on a 144 Hz screen would look like judder, so rendering **interpolates** the camera between the last two physics states using whatever fraction of a tick is left in the accumulator:

<CodeRef lang="cpp" repo="https://github.com/Ollie1o1/3d_shooter" file="src/GameplayState.h" lines="2284-2288" code={"void render() override {\n    float alpha = (float)(accumulator / PHYSICS_DT);\n    glm::vec3 renderCamPos = glm::mix(prevCamPos, player.camera.position, alpha);\n    Camera renderCam = player.camera;\n    renderCam.position = renderCamPos;"} />

### Movement that rewards skill

The obvious implementation, `velocity = direction * speed`, feels dead: no momentum, and nothing to master. OVERDRIVE uses Quake's acceleration model instead. It projects the current velocity onto the direction you're pressing and only adds speed up to a cap **along that direction**:

<CodeRef lang="cpp" repo="https://github.com/Ollie1o1/3d_shooter" file="src/Player.h" lines="241-259" code={"// WASD acceleration \u2014 suppressed while sliding so momentum carries.\nif (!sliding) {\n    glm::vec3 wishDir{0.f};\n    if (keys[SDL_SCANCODE_W]) wishDir += flatFwd;\n    if (keys[SDL_SCANCODE_S]) wishDir -= flatFwd;\n    if (keys[SDL_SCANCODE_D]) wishDir += flatRight;\n    if (keys[SDL_SCANCODE_A]) wishDir -= flatRight;\n\n    float accel = onGround ? acceleration : airAcceleration;\n\n    if (glm::length(wishDir) > 0.001f) {\n        wishDir = glm::normalize(wishDir);\n        glm::vec3 hVel{velocity.x, 0.f, velocity.z};\n        float currentSpeed = glm::dot(hVel, wishDir);\n        float addSpeed = glm::clamp(horizontalSpeed - currentSpeed, 0.f, accel * dt);\n        velocity.x += wishDir.x * addSpeed;\n        velocity.z += wishDir.z * addSpeed;\n    }\n}"} />

Because the cap is on the *projection*, turning the camera while strafing in the air keeps finding directions where `currentSpeed` is below the cap, so a skilled player can gain speed beyond the normal maximum. That's the same mechanic behind strafe-jumping in Quake and the movement feel of Titanfall and ULTRAKILL. Air acceleration is about half of ground acceleration (42 vs 80), friction drops to a quarter during a slide, and it's skipped entirely while grappling so the hook can build speed. Getting the grapple and dash to feel right took five separate commits of tuning and fixes.

### Encounters you can read

An early version had cube enemies wandering two huge rooms, and it wasn't fun: you couldn't tell enemies apart at a distance, couldn't see an attack coming, and spent most of the time looking for the last one. The redesign started from what each enemy should *ask of the player*. A Husk fires slow orbs you can parry; a Ripper crouches before it lunges, so you dash; a Sentinel paints you with a laser before its burst, so you break line of sight; a Brute slams the ground, so you jump the shockwave; a Mite explodes, so you shoot it early and its blast hurts its friends instead.

That only works if the player can read it, so every enemy is a rig of boxes on joints (hips, shoulders, wing roots), posed from its AI state each frame. Legs swing with the walk cycle, a Raptor's wings flap, and arms come up to aim or overhead to slam during a wind-up. Each rig is 11 to 30 boxes, and all of them, plus death debris, projectiles, doors and jump pads, go to the GPU as one instanced draw call.

Waves are run by a small director that keeps 6 to 10 enemies on the field and trickles the rest in, away from the player:

<CodeRef lang="cpp" repo="https://github.com/Ollie1o1/3d_shooter" file="src/WaveDirector.h" lines="84-90" code={"} else if (!queue.empty() && aliveCount < current().maxAlive && spawnTimer <= 0.f) {\n    Queued q = queue.front();\n    queue.erase(queue.begin());\n    out.push_back({q.type, q.fixed ? q.pos : pickSpawn(q.type, playerPos)});\n    spawnTimer = SPAWN_GAP;\n    ++aliveCount;   // it's on the field now; don't call the wave clear this tick\n}"} />

That last line is a bug fix. Without it, the wave-clear check right below compared against the alive count from *before* the spawn, so a wave whose last enemy spawned into an empty field ended instantly. The boss wave is a single enemy, so it always did. The director and the enemy AI have no OpenGL in them, which is what made this findable: a headless test drives the director through an entire simulated run, and a regression test now holds the boss wave open while the boss is alive.

### Climbing, and a time trial

The fourth arena, the Spire, is built around height: a 26 m tower with ledges, bridges, a balcony and a summit. Each wave spawns a tier higher, and the riflemen up there won't step off their perch (a ledge check in their steering treats a drop like a wall), so you have to climb to them. Rippers and Mites have no such check and jump down after you.

Lifts, sweepers and orbiting platforms connect the tiers, and you can grapple any of them. They needed almost no new machinery: a moving platform is an ordinary wall flagged as dynamic. It moves every physics tick and records how far it went. It's kept out of the spatial grid and tested every tick instead. The player remembers which wall it is standing on, and riding a platform is just adding that platform's movement before the physics step. A test sweeps every platform through two full cycles and fails if any of them ever passes through a wall.

Fast mode reuses the same wave director with a flag: a section's enemies are hand-placed and appear all at once, sections chain with no intro or break, and clearing the last one lights a finish beacon instead of ending the run. A headless test runs the whole descent and checks that every placed enemy appears exactly once, exactly where it was placed.

### A renderer with no art assets

There isn't a single image file in the repository. Floor grids, brick walls, metal ceilings and crates are generated at startup from value noise and uploaded as textures:

<CodeRef lang="cpp" repo="https://github.com/Ollie1o1/3d_shooter" file="src/TextureGen.h" lines="18-31" code={"inline float hash(float x, float y) {\n    float h = sinf(x * 12.9898f + y * 78.233f) * 43758.5453f;\n    return h - floorf(h);\n}\n\ninline float smoothNoise(float x, float y) {\n    float ix = floorf(x), iy = floorf(y);\n    float fx = x - ix, fy = y - iy;\n    fx = fx * fx * (3.f - 2.f * fx);\n    fy = fy * fy * (3.f - 2.f * fy);\n    float a = hash(ix, iy), b = hash(ix+1, iy);\n    float c = hash(ix, iy+1), d = hash(ix+1, iy+1);\n    return a + (b-a)*fx + (c-a)*fy + (a-b-c+d)*fx*fy;\n}"} />

The frame renders to an offscreen framebuffer, with all enemies in a single instanced draw call, then goes through bloom: a bright-pass extract followed by **ten** separable Gaussian blur passes that ping-pong between two framebuffers, alternating horizontal and vertical:

<CodeRef lang="cpp" repo="https://github.com/Ollie1o1/3d_shooter" file="src/PostProcess.h" lines="116-125" code={"bool horizontal = true;\nfor (int i=0;i<10;++i) {\n    glBindFramebuffer(GL_FRAMEBUFFER,bloomFBO[horizontal?1:0]);\n    blurShader.use();\n    blurShader.setInt(\"image\",0);\n    blurShader.setInt(\"horizontal\",horizontal?1:0);\n    glBindTexture(GL_TEXTURE_2D,bloomTex[horizontal?0:1]);\n    drawQuad();\n    horizontal = !horizontal;\n}"} />

The optional CRT pass adds barrel distortion, chromatic aberration and scanlines on top, before the HUD and the weapon view model are drawn.

### Porting it to the browser

The same C++ runs above as WebAssembly, drawing through WebGL2. Most of the port was small because WebGL2 is OpenGL ES 3.0, and every GL call the game makes already exists there. The differences that mattered:

- **Shader dialect.** Desktop GLSL 3.30 and GLSL ES 3.00 are close, so the loader rewrites the `#version` line and adds default precision at load time, and the same `.frag` files serve both builds. ES doesn't allow implicit int-to-float conversion, so one blur shader needed explicit casts. It also bans initializers on uniforms, which the sky shader had.
- **Who owns the loop.** A browser tab can't block in `while (running)`, so the frame body moved into an `App` struct that the desktop build calls in a loop and the web build hands to `requestAnimationFrame`. The state lives on the heap because the web `main()` returns before the first frame runs.
- **Escape belongs to the browser.** Pressing Esc releases pointer lock before the game ever sees the key, so losing the lock mid-run now pauses the game. `P` pauses too.
- **The mouse can lie.** Under pointer lock, Chrome occasionally reports one enormous mouse delta, which snapped the view round 180°. The page now asks for raw input (`unadjustedMovement`) where the browser supports it, and the game drops a single delta that is many times larger than the ones around it. Two large deltas in a row are a real flick and still go through.
- **Saving.** Emscripten's filesystem lives in memory and is forgotten on reload, so settings and best times go to `localStorage` instead.

On an M2 MacBook it holds 60 fps in Chrome, the same as the native build at that refresh rate.

### What an audit turned up

Before putting the game in front of people I read it end to end, and wrote a small headless test harness for the parts that could be tested without a window. Most of what it found was invisible in a quick playtest, which is exactly why it had survived.

- **Standing on a platform flickered between grounded and airborne.** Gravity is skipped while grounded, so on the next tick the player no longer overlapped the box and read as airborne, then fell a hair and landed again. It alternated every tick, so the landing sound fired about 30 times a second. A test that stands the player on a box for 120 ticks counted 60 ground-to-air transitions. After adding a ground probe (a box top within 2 cm under the feet counts as ground) it counts zero.
- **Hitscan went through walls.** The revolver and shotgun picked the nearest enemy the ray hit and only clipped the *tracer* at the wall, so you could shoot enemies behind cover. A hit now counts only if the enemy is closer than the nearest wall along the ray.
- **A use-after-free on every menu click.** Clicking Start ran a callback that replaced the current game state, destroying the menu while its own event handler was still running. State changes are now queued and applied between frames.
- **Most of the level rendered at 15% brightness.** The world shader darkens pixels near a face's UV edge to outline boxes, but world-space UVs run past 1.0, so everywhere outside one 4 m tile counted as "on an edge". Wrapping the UVs with `fract()` fixed it, and is a big part of why the arenas now have colour.
- **Settings that did nothing.** The volume slider was saved and displayed but never reached the mixer, and the field-of-view setting was ignored on the first run because the constructor read it before it was injected.
- **A whole enemy type that couldn't hurt you.** Stalkers had a wind-up duration configured but no attack, so they just followed you around. They now lunge with a telegraphed melee hit and knockback.

`make test` runs the physics checks (grounding on floors and box tops, walking off ledges, jump arcs, wall blocking) and the game-logic checks (every spawn point clear of walls, every jump pad landing on its platform, each enemy type doing its attack, platforms that never clip walls, no scenery inside an arena, the weapon and XP numbers, and full simulated Arena and Fast runs) with no GPU or window.

## Results

- A complete game loop: a menu with two modes, settings that persist between launches (FOV, sensitivity, zoom sensitivity, volume, FPS cap, screen shake and more), four arenas with their own lighting, fog and procedural sky, a boss fight, a time trial with splits and saved best times, XP and weapon upgrades, checkpoint retries, style scoring, a pause menu, and victory/death screens.
- Procedurally synthesized sound effects to match the procedural textures, so the repository still has no recorded or drawn assets.
- Consistent movement across refresh rates, thanks to the fixed step and interpolation.
- Builds and runs on macOS, Windows and in the browser. It also compiles and passes its physics tests on Linux (Ubuntu 24.04), but I haven't played it on a Linux desktop, so I don't claim Linux support yet.

## What I'd do next

- **Continuous collision for the grapple.** Resolution is discrete today, so at grapple speeds a thin wall could in principle be skipped in a single tick. Sweeping the player's box along its velocity would remove that risk.
- **Touch controls for the web build.** Phones can run it but have no way to aim; twin virtual sticks would open it up to anyone visiting on mobile.
- **GPU timing.** Add timer queries per pass to see what the ten blur passes actually cost, then try a downsampled bloom chain.
