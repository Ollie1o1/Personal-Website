## Overview

The NES is a good first "real" machine to emulate: small enough to hold in your head, but with three chips (a Ricoh 2A03 CPU, a picture processing unit and an audio processing unit) that have to agree on time down to the cycle, or games break in visible ways.

This emulator implements the 6502 instruction set including the common unofficial opcodes, a PPU with Loopy scroll registers that renders dot by dot into a 256×240 frame, an APU with both pulse channels, triangle, noise and DMC, and three cartridge mappers (NROM, MMC1 and UxROM). Between them those cover games like Super Mario Bros, The Legend of Zelda, Mega Man and Castlevania. Battery-backed cartridge RAM is saved to disk, and it ships with six homebrew ROMs to play out of the box.

The big design decision is **ownership**. A naive Rust port of a C-style emulator ends up wrapping every component in `Rc<RefCell<…>>` so the CPU can reach the PPU and the PPU can reach the cartridge. That compiles, but it moves the borrow checker's job to runtime and hides the real data flow. Here the `Emulator` owns the CPU and a single `Bus`; the bus owns everything the CPU can address. The CPU takes `&mut Bus` for the duration of one instruction and gives it back. There are zero `RefCell`s in the codebase, so aliasing mistakes are compile errors rather than runtime panics.

## Hard problems

### Three chips, one clock

On NTSC hardware the PPU runs exactly three dots for every CPU cycle, and the APU and mapper tick once per cycle. The emulator makes the CPU the master clock: execute one instruction, learn how many cycles it took, then advance everything else by that many cycles and collect interrupt lines on the way out.

<CodeRef lang="rust" repo="https://github.com/Ollie1o1/better_emulator" file="src/emulator.rs" lines="90-116" code={"let cpu_cycles = self.cpu.step(&mut self.bus);\n\nfor _ in 0..cpu_cycles {\n    self.total_cycles += 1;\n\n    for _ in 0..3 {\n        if self.bus.ppu.tick(&mut self.bus.cartridge) {\n            frame_done = true;\n        }\n        if self.bus.ppu.nmi_occurred {\n            self.bus.ppu.nmi_occurred = false;\n            self.cpu.nmi_pending = true;\n        }\n    }\n\n    self.bus.apu.tick();\n\n    if self.bus.cartridge.irq_active() {\n        self.bus.cartridge.irq_clear();\n        self.cpu.irq_pending = true;\n    }\n\n    if self.bus.apu.frame_irq {\n        self.bus.apu.frame_irq = false;\n        self.cpu.irq_pending = true;\n    }\n}"} />

Interrupts are raised by components the CPU doesn't own a reference to, so they're flags the loop reads and forwards. The same function also handles OAM DMA, which stalls the CPU while 256 bytes are copied into sprite memory (after an alignment cycle on odd clocks) while the PPU keeps running.

### The NMI that only fired once

In the first version, the vertical-blank interrupt fired on the first frame and never again. The PPU raises a non-maskable interrupt at the start of vertical blank, and NMI on the NES is **edge-triggered**: the CPU only sees it when the line goes from low to high. My edge detector remembered the previous level in `nmi_prev` and re-evaluated it when vblank was set, or when the game read `$2002` or wrote `$2000`, but not when the pre-render scanline *cleared* vblank. A game that didn't touch those registers during vblank left `nmi_prev` stuck high, so the next frame's rising edge was never seen.

<CodeRef lang="rust" repo="https://github.com/Ollie1o1/better_emulator" file="src/ppu/mod.rs" lines="194-200" code={"fn update_nmi(&mut self) {\n    let nmi = self.nmi_output && (self.status & 0x80 != 0);\n    if nmi && !self.nmi_prev {\n        self.nmi_occurred = true;\n    }\n    self.nmi_prev = nmi;\n}"} />

The fix was one line in the right place: re-evaluate the edge when the pre-render scanline clears the vblank flag, so the falling edge is recorded every frame no matter what the game does.

<CodeRef lang="rust" repo="https://github.com/Ollie1o1/better_emulator" file="src/ppu/mod.rs" lines="289-293" code={"fn tick_prerender(&mut self, cart: &mut Cartridge) {\n    if self.dot == 1 {\n        self.status &= !0xE0; // clear vblank, sprite-zero-hit, overflow\n        self.update_nmi();    // falling edge: reset nmi_prev so next vblank re-triggers NMI\n    }"} />

The same commit fixed the background pipeline's order to fetch, then render, then shift, matching hardware (render reads the shift register before it advances), and limited pre-render fetches to the dot ranges the real PPU uses.

### Reading a controller the way the hardware does

Controllers are read serially: the game writes 1 then 0 to a strobe register, and each subsequent read shifts out one button. My first version captured the buttons whenever strobe was written high. The real 4021 shift register reloads continuously while strobe is high and freezes on the **falling** edge, and after eight reads it returns 1s. The fix latches on the 1 → 0 transition:

<CodeRef lang="rust" repo="https://github.com/Ollie1o1/better_emulator" file="src/controller/mod.rs" lines="23-31" code={"pub fn write(&mut self, val: u8) {\n    let new_strobe = val & 1 == 1;\n    // Latch on falling edge (1 \u2192 0): freeze current button state into shift register.\n    // While strobe is high the shift register is continuously refreshed; reads return A.\n    if self.strobe && !new_strobe {\n        self.shift = self.buttons;\n    }\n    self.strobe = new_strobe;\n}"} />

## Results

- Boots and plays NROM, MMC1 and UxROM cartridges, including the six bundled homebrew titles; battery-backed saves persist to a `.sav` file next to the ROM.
- Presentation details that matter to how it *feels*: an 8:7 pixel aspect ratio (NES pixels aren't square), CRT-style scanlines, and a status bar with live input state, FPS and volume.
- Two-player input, and adding a mapper is a three-step change (implement the `Mapper` trait, add an enum variant, match the iNES id).
